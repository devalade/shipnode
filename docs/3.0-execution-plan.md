## Sprint 2c — Migration downstream vers `config.apps[i]`

### Objectif
Les consumers internes (services, strategies, CLI commands, domain modules) lisent les fields per-app depuis `config.apps[i]` plutôt que depuis les legacy top-level mirrors. Pour la transition: `i = 0` partout — c'est encore single-app sous le capot. La vraie itération multi-app vient en 2d.

### Stratégie recommandée
Créer un helper unique `src/domain/workspace.ts` qui expose:

```ts
export function getActiveApp(config: ShipnodeConfig, name?: string): ShipnodeApp {
  if (name) {
    const found = config.apps.find((a) => a.name === name);
    if (!found) throw new Error(`No app named "${name}" in this workspace`);
    return found;
  }
  return config.apps[0];
}
```

Tous les consumers downstream appellent `getActiveApp(config)` (ou `getActiveApp(config, opts.app)` quand le `--app` flag arrive en 2e). Ça centralise le point de migration pour passer du single-app au multi-app.

### Fichiers à migrer (par couche)

**Domain + services** (impact métier):
- `src/domain/deploy/backend-strategy.ts`
- `src/domain/deploy/frontend-strategy.ts`

- `src/services/caddy.service.ts`
- `src/services/deploy.service.ts`
- `src/services/health.service.ts`

**CLI commands** (adapters):

### Pattern de migration

Pour chaque fichier, remplacer:

| Avant | Après |
|---|---|

| `config.domain` | `getActiveApp(config).domain` |

## Sprint 2d — Strategies + orchestrator vraiment multi-app

### Objectif
Le deploy orchestrator itère sur `config.apps[]` et déploie chaque app séquentiellement. Le layout disque devient per-app: `${remotePath}/${app.name}/releases/<ts>/` et `${remotePath}/${app.name}/current`.

### Changements clés
- `src/domain/deploy/orchestrator.ts`: boucle sur `config.apps`, appelle la strategy appropriée (backend/frontend) par app. Stop sur première erreur. Affiche un résumé total à la fin.
- `src/domain/deploy/backend-strategy.ts` et `frontend-strategy.ts`: signature change — prend `(workspace: ShipnodeConfig, app: ShipnodeApp)` au lieu de `(config: ShipnodeConfig)`. `app` est l'app à déployer, `workspace` donne accès à ssh/database/etc. partagés.
- `src/services/caddy.service.ts`: génère **un site block par app** ayant un `domain`. Le `Caddyfile` agrège tous les sites du workspace.
- Layout disque per-app:
  - `${remotePath}/${app.name}/releases/<ts>/`
  - `${remotePath}/${app.name}/current` → release active
  - `${remotePath}/${app.name}/shared/${app.envFile}` → .env de cette app
  - Le `${remotePath}/shared/` partagé disparaît (chaque app a son shared)
- Rollback per-app: `${remotePath}/${app.name}/.releases.json` historique séparé par app

### Compat single-app
Une config 2.x (qui n'utilise pas `.apps([])`) produit `apps = [{ name: 'app', ... }]` après assemble. Le layout disque devient donc `${remotePath}/app/releases/<ts>/` au lieu de l'ancien `${remotePath}/releases/<ts>/`.

**ATTENTION**: c'est un break disque pour les déploiements existants en place. Deux options:
- **Option A** (recommandé): au premier deploy 3.0 sur un serveur existant, détecter l'ancien layout (`${remotePath}/releases/` existe), faire une migration automatique (`mv ${remotePath}/releases ${remotePath}/app/releases` + `ln -sf app/current current`). Documenter dans le migration guide.
- **Option B**: garder l'ancien layout flat quand `config.apps.length === 1` et `apps[0].name === 'app'` (sentinelle "auto-named"). Évite la migration disque mais perpétue 2 code paths.

Choisir Option A — moins de dette technique. Faire la migration disque dans une nouvelle commande `shipnode migrate` ou directement au début du deploy si detected.

### Critère d'acceptance
- `pnpm test` passe avec les nouveaux tests multi-app
- Tests existants single-app continuent à passer après ajustements de path
- `tests/unit/orchestrator.test.ts` couvre: deploy de 2 apps séquentiel, échec sur app[0] empêche app[1], résumé final
- `tests/unit/backend-strategy.test.ts` et `frontend-strategy.test.ts` adaptés à la nouvelle signature
- `tests/unit/caddy.service.test.ts` (à créer si absent) couvre: génération du Caddyfile avec N site blocks
- Le grep `config\.apps\[0\]` ne doit revenir QUE depuis le helper `getActiveApp` (toute itération sur les apps passe par `for (const app of config.apps)`)

### Commits (peut être split)
- `refactor(deploy): orchestrator iterates over config.apps (sprint 2d)`
- `feat(deploy): per-app release directories at ${remotePath}/${app.name}/`
- `feat(caddy): one site block per app having a domain`

## Sprint 2e — CLI `--app <name>` flag

### Objectif
Les commandes `deploy`, `env`, `restart`, `stop`, `logs`, `status`, `metrics`, `run` acceptent un flag `--app <name>` qui les fait opérer sur une app spécifique. Sans flag, elles opèrent sur **toutes les apps** du workspace (séquentiellement pour deploy/env/restart/stop; agrégé pour logs/status/metrics).

`rollback` **exige** `--app` (rolling back tout le workspace ne fait pas sens — voir ADR).

`cloudflare init`, `cloudflare audit`, `cloudflare status`, `harden`, `doctor`, `setup`, `backup setup` restent **workspace-level** (n'acceptent pas `--app`).

### Implémentation
- Ajouter `--app <name>` option dans chaque CLI command concernée (via `commander`)
- Le command appelle `getActiveApp(config, opts.app)` — déjà en place depuis 2c
- Pour `deploy`/`env`/`restart`/`stop` sans `--app`: itérer `for (const app of config.apps)` et appeler la logique pour chaque
- Pour `logs`/`status`/`metrics` sans `--app`: tag chaque ligne d'output avec le nom de l'app
- Pour `rollback` sans `--app`: erreur explicite "`rollback requires --app <name>; available: ${apps.map(a=>a.name).join(', ')}`"

### Critère d'acceptance
- Tests CLI commands updated pour vérifier le flag
- Tests pour le mode "sans --app" sur un workspace multi-app: deploy toutes les apps en séquence
- Test rollback sans --app → throw explicite

### Commits (split possible)
- `feat(cli): --app <name> flag on deploy/env/restart/stop (sprint 2e)`
- `feat(cli): --app on logs/status/metrics/run with per-app prefix`
- `feat(cli): rollback requires --app explicitly`

## Sprint 2f — Cleanup legacy top-level mirrors

### Objectif
Maintenant que tous les downstream lisent `apps[i]`, les legacy top-level mirrors (`config.app`, `config.domain`, `config.pm2`, etc.) ne sont plus consommés par le code de shipnode lui-même. On peut les retirer du shape canonique pour ne pas perpétuer la dette.

### Changements
- `src/shared/types.ts`: retirer les legacy fields top-level de `ShipnodeConfig`. Garder uniquement les workspace-level fields + `apps: ShipnodeApp[]`.
- `src/config/schema.ts`:
  - Retirer les legacy fields top-level de `ShipnodeConfigBaseSchema`.
  - Retirer les refines top-level (`frontend cannot declare pm2` et `domain requires web app`) — ils vivent désormais uniquement sur `ShipnodeAppSchema`.
  - **Garder** la `z.preprocess` qui synthétise `apps[0]` depuis les legacy fields d'INPUT (c'est ce qui permet à une config 2.x de continuer à parser).
- `src/config/assembly.ts`: retirer le post-parse mirror. `assembleConfig` redevient le 5-liner de Sprint 1 (normalize pm2 + parse). Plus de mirror.
- `tests/unit/assembly.test.ts`: retirer les tests qui asserentaient `config.domain === config.apps[0].domain` etc.

### Compat externe
Si un user externe lisait `config.domain` directement (ex: dans un script appelant `loadConfig()`), ça casse. C'est OK — c'est une 3.0 major, et le migration guide (Sprint 5) documente le changement.

### Critère d'acceptance
- `pnpm test` passe
- `pnpm lint` clean
- Le shape `ShipnodeConfig` exporté n'a plus de fields per-app au top level
- Le z.preprocess fait toujours son job pour les configs 2.x en input
- Test ajouté: une config 2.x avec `app: 'backend'`, `domain: 'x'`, `pm2: {...}` parse et produit `apps[0]` correct, MAIS `config.domain` (top-level) est `undefined` (et probablement non-typé maintenant)

### Commit

## Sprint 4 — `domain/cloudflare/` + multi-hostname tunnel

### Objectif
Cloudflare devient un objet de domaine de premier rang. `cloudflare init` devient idempotent et gère plusieurs hostnames sur un même tunnel naturellement.

### Modèle domain
Créer `src/domain/cloudflare/`:
- `tunnel.ts`: `class Tunnel { name, id?, credentialsPath, ingress: Ingress[], catchAll }` avec méthodes `addIngress(hostname, service)`, `toYaml()`, `fromYaml(content)`.
- `ingress.ts`: `interface Ingress { hostname: string, service: string }` (service est `http://localhost:${port}` typiquement).

### Refactor de `cloudflare init`
- Lire l'éventuel `/etc/cloudflared/config.yml` existant côté serveur
- Construire/mettre à jour le `Tunnel` depuis l'état serveur + le workspace local
- Pour chaque `app` du workspace ayant `domain` ET `pm2.apps` avec port:
  - `tunnel.addIngress(app.domain, 'http://localhost:${webPort}')`
  - `cloudflared tunnel route dns ${tunnelName} ${app.domain}` (idempotent)
- Émettre `tunnel.toYaml()` → `/etc/cloudflared/config.yml`
- `systemctl restart cloudflared`
- Optionnel: lock down firewall (UFW) si `cloudflare.lockdownFirewall === true`

### Breaking
- `CloudflareConfig.appHostname` **supprimé**. Émettre un warning si présent dans la config + fallback sur `apps[0].domain` pour le run en cours.
- `CloudflareConfig.sshHostname` reste (cas d'usage SSH-over-tunnel toujours pertinent).

### Critère d'acceptance
- Test unitaire `tests/unit/cloudflare.tunnel.test.ts`: `Tunnel.fromYaml().addIngress(...).toYaml()` round-trip
- Test orchestrator: deux apps → deux ingress entries + deux DNS routes + un seul service systemd
- Le YAML émis est diffable et propre (ingress entries triées par hostname pour stabilité)

### Commit
`feat(cloudflare): multi-hostname tunnel via domain/cloudflare model (sprint 4)`
